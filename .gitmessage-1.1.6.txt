1.1.6：桌面版关闭真正生效、确认框自绘、存活判定改走插件路由

三处都在修"桌面版下点了没反应"，根因各不相同。

1. 关闭在桌面版关不掉。
   桌面版宿主是 Electron 主进程 fork 出来的子进程，它的 ctx.appExit 就是
   DSH 的 shutdown(code)，而 @deepseek-ai/dsh 0.2.x 的实现是
   `shutdown(code){ return start(code, false) }`（forceAfterDispose = false），
   走 completeOnce 即 process.exitCode = code，不调用 process.exit；只有
   dispose 卡住超过 5 秒才强制结束。
   命令行宿主能退出是因为 CLI 主进程自己结束了，而 Electron 主进程的事件循环
   由 app 持有，设退出码不会让它退出。于是路由回成功、页面显示"正在关闭"、
   DSH 还在跑。

   桌面版自己的停止通道是 IPC：主进程发 { type: 'shutdown' }，
   dsh-desktop-host 收到后执行 await shutdown.shutdown(0)、回报
   { type: 'shutdown-complete' }、再 process.disconnect()。
   新增 isDesktopHost() 以"存在 process.send 且 connected === true"判定，
   requestDesktopShutdown() 发出该消息；仅在通道不可用时才退回
   appExit → SIGTERM 的原有路径。

   用 IPC 通道而不是可执行文件名判定：源码检出、打包安装、自定义安装的
   可执行文件名各不相同，而 IPC 通道是"被 fork 出来"这一事实本身，
   命令行宿主没有它。connected 单独判断，因为父进程已消失时 send 仍在、
   消息会被丢弃，把它当作成功正是页面一直显示"正在关闭"的成因。

2. 完成判定永远"仍在运行"。
   原探针请求 window.location.href。桌面版页面来自 dsh-app://app/，
   由 Electron 主进程的 protocol.handle 提供——宿主进程退出后它仍应答 200，
   因此永远 reachable。改为主机自己的 /config 路由（HEAD 请求），
   只有宿主进程活着才应答。

3. 确认框无 UI 且只有两个按钮。
   宿主不提供 Modal 时原实现退回 window.confirm，而它结构上就只有
   取消和确定，不可能给出第三个"重启"。改为插件自绘对话框
   （FallbackConfirmDialog）：backdrop + 标题 + 正文 + 三个按钮，
   支持 Escape 关闭，样式沿用已有 CSS 变量。
   点击 backdrop 不取消，因为这是结束进程的确认，误点不应吞掉询问。
   勾子属性与宿主 Modal 保持同名，测试和页面脚本按同一名字查找。

4. 兼容范围补上 0.2.0 线（dshhub.compatibility.dsh、engines.dsh、
   peerDependencies 三处同步）。上一版只改了两处，dshhub.compatibility.dsh
   漏改，这次补齐。

README 与 README.zh 的"桌面版"一节按实测重写：删掉"没有 ctx.appExit
因此退化为强制退出"这一条（实测不成立），补上 IPC 通道的原理、探针
位置、自绘确认框，以及升级时须显式写 tag 的提醒。

测试 235/235 通过。新增 7 个测试覆盖桌面版检测：无 IPC 通道、
父进程已断开、send 抛异常、send 不存在、非对象输入。原"原生 confirm"
测试改写为"宿主无 Modal 时自绘对话框"，并新增一项三选一的功能对等测试。
